# 劇場字幕機

這個專案提供一個含「控制端」與「檢視端」的劇場字幕機。控制端可以直接貼上劇本文字並呼叫 OpenAI 拆解成字幕句子、即時編輯與播放；檢視端預設顯示目前字幕，可切換固定跟隨 CUE 的提詞模式，適合給觀眾或表演者在手機/平板上即時查看。

## 專案結構

```
server/  Node.js + Express + Socket.IO 後端服務
client/  Vite + React 控制端/檢視端前端
```

## 本地開發

1. 安裝依賴
   ```bash
   cd server && npm install
   cd ../client && npm install
   ```

2. 開啟開發伺服器
   - 後端：`cd server && npm run dev`（預設 http://localhost:3000）
   - 前端：另開一個終端 `cd client && npm run dev`（預設 http://localhost:5173）

   Vite dev server 已設定 proxy，開發時可直接造訪：
   - 控制端：http://localhost:5173/control
   - 檢視端：使用控制端「分享」中的 `/viewer/場次token` 連結

3. 若想以單一伺服器提供前端與 API：
   ```bash
   cd client && npm run build   # 建立前端靜態檔
   cd ../server && npm start    # 伺服器會自動提供 client/dist
   ```
   然後造訪 http://localhost:3000/ ，輸入共用密碼後進入系統。

## 使用流程（控制端）

1. 先進入首頁並輸入共用密碼，登入系統後可查看既有節目或建立新節目。
2. 開啟「設定 → 系統連線」輸入 OpenAI API Key（可以勾選「在此裝置記住」以存入瀏覽器 localStorage）。
3. 開啟「工具 → 劇本準備與解析」，先貼上第一語言劇本並點「解析」。系統使用所選模型辨識角色與台詞／舞台指示，先由程式產生候選分段，再由 AI 依前後文審核切點、合併短格或拆分意群。AI 只回傳原文單位的連續範圍，程式驗證沒有遺漏、重複或順序變動後才套用，不由 AI 改寫台詞。
   - 中文以 20 個全形字寬為目標，AI 可為完整語意放寬至 24；英文等拉丁語系以 60 字寬為目標、72 為上限（字母通常算 0.5 字寬），並保留完整單字。最終只對超過上限的台詞再拆分，不把每個逗號都切成短格。
   - 連續舞台指示合併為一格，各條指示保留換行；不跨台詞合併，也不套用台詞長度限制。舞台指示保留給控制端／提詞端，觀眾與投影不顯示；單獨角色頭銜轉成角色資訊。
   - 分段審核回應不完整、超過上限或服務失敗時，保留程式分段並顯示人工檢查提示。完整劇本分批處理；這些 API 呼叫只發生在匯入解析時，不影響正式演出的辨識流程。
   - 角色辨認只會在劇本解析階段執行；在字幕格手動輸入、分段、合併或匯入的文字會原樣保存。若要修改角色，請使用字幕行的「設定角色」功能。
   - 其他語言請貼上完整既有譯文，按「依原文字幕格全文對齊」。系統直接把全部原文字幕格 JSON 與完整譯文交給所選模型，一次建立完整意群的對照區段並分配每格譯文；不再先獨立拆譯文或按格數順序填入。相鄰多格合起來意思一致即可，允許不同語種在同一意群中先說結果再說原因。
   - 對齊結果先暫存，程式檢查格子 ID／順序、譯文全文涵蓋及單字邊界，再由另一次 AI 請求參考全部原文、全部譯文和整份結果覆核。正常為兩次主要請求；有問題時最多修正兩次並重新檢查／覆核，修正不能改動未指定的格子。AI 回傳文字只作定位，實際保存的是原譯文中的片段；允許換行與空白格式不同，不允許改標點、潤飾、重排、遺漏或重複。行首人物標籤與場景標題另外完整保留在原稿中。
   - 第一語言格數、ID、角色、舞台與音樂資料及其他語言保留；對齊只更新選定語言，不新增格子。無法確認的意群、過長譯文或空白台詞格會標記「譯文待確認」，可編輯後按「已檢查，確認此格」。標記與確認可保存、備份及復原，文字再更動會提示重新核對；這些資訊只在控制端顯示。
   - 對齊／覆核失敗、文字完整性未通過或等待期間原文／格子結構／同一語言已被編輯時，不套用結果，保留現有字幕與貼上的譯文。原文與譯文的全文都不會自動截斷；只有模型實際回報容量不足，且兩份資料有相同順序、編號可核對的 ACT／SCENE／第X幕／第X場標題時，才改為完整場景逐場分配與覆核，並明確標示未完成單次全文覆核。缺少可靠場景邊界時會保留原字幕，提示更換可處理全文的模型。
   - 使用 [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) 約束回應格式；程式另外驗證全文內容及拒答／未完成回應。這保證的是資料完整性，語意分配品質仍需用實際劇本與認可的對齊 JSON 比較。
   - 全文分配與修正的回應上限依所選模型設定，避免另設過短上限截斷大模型結果；規格依據：[GPT-4o](https://developers.openai.com/api/docs/models/gpt-4o)、[GPT-4o mini](https://developers.openai.com/api/docs/models/gpt-4o-mini)、[GPT-5.5](https://developers.openai.com/api/docs/models/gpt-5.5)。覆核可合併相鄰問題區段，單次 API 請求保留 10 分鐘等待時間。
4. 第一語言或其他語言解析成功並寫入字幕後，解析視窗會自動關閉，回到字幕清單；失敗時保留視窗供修正或重試，完成訊息與檢查提示仍會顯示在主畫面。字幕清單可直接編輯（contentEditable）。單擊某一句或使用鍵盤方向鍵 `↑` / `↓` 會切換外部字幕；雙擊文字本身可直接進入編輯，不會再把畫面捲走。
5. 控制端可分別指定「檢視端預設語言」與「投影端播放語言 / 顯示模式」；檢視端初次進入會先套用預設語言，但觀眾之後仍可自行切換單語或全部語言。投影端保持乾淨，只會持續跟著控制端指定的單語、雙語並置或全部語言並置設定。
6. 角色資訊會保留在字幕資料裡，控制端可集中新增、改名或刪除角色；是否以顏色區分角色也由控制端切換，檢視端與投影端會同步套用。
7. 需要暫時關閉觀眾字幕時，點「遮蔽檢視端字幕」即可讓檢視端畫面變成空白，但控制端仍可瀏覽全文、以 `Command + F` 搜尋並點擊跳轉。
8. 同一節目的字幕內容由所有場次共用；修改、增刪、排序、翻譯、角色或音樂標記後，每個場次都會使用同一份最新字幕。各場次仍各自保留播放位置與顯示狀態。
9. 每個場次建立時都會取得固定的觀眾網址與 QR code。控制端可預先下載所有場次的 QR code；觀眾進入尚未被控制的場次時會停留在等待頁，控制端切換到該場次後會自動開始顯示字幕。
10. 若要手動備份節目，可在控制端使用「匯出節目備份 JSON」；備份會保留原本 `sessionId`、viewer/projector token、預設播放語言、語言、角色、所有場次與共用字幕內容。
11. 若要還原備份，可在首頁或控制端使用「匯入節目備份 JSON」；若備份中的 `sessionId` 已存在，系統會拒絕匯入，避免悄悄改號。

## 檢視端連線方式

- 將控制端畫面顯示的分享連結複製給觀眾或表演者，他們可在任何支援瀏覽器的裝置上開啟（建議橫式）。
- `/viewer/<場次token>` 預設為觀眾模式；頁面可切換「觀眾模式／提詞模式」。分享提詞模式連結使用同一網址加 `?mode=prompter`，舊 `/prompter/<token>` 連結會自動轉入新介面。
- 提詞模式最多顯示目前格、前兩句及後六句，不顯示段落標籤與格號，隨控制端更新；不提供手動捲動、拖曳或鍵盤翻頁。小螢幕或長台詞會先縮減附近台詞，再縮小目前台詞，優先完整顯示目前格。仍可切換語言、調整字級及使用瀏覽器縮放。
- 所有持有觀眾連結的人都能切換提詞、看見附近台詞（含舞台指示）。這不是限制劇本存取的權限機制；後端仍保留舊版全文提詞 API 以相容舊客戶端。
- 新提詞訂閱每次最多傳送附近九格，不反覆傳送整份劇本；切換模式沿用同一連線與場次，不改變控制端 CUE。兩個模式共用遮蔽、角色顏色與音樂提示；目前場次尚未開始時顯示等待頁。即時字幕只顯示已收到的文字，不預測後續台詞。
- 檢視端只能接收字幕及設定本機顯示偏好，無法控制節目或讀取控制端私有資料。

## 自動跟隨劇本字幕

控制頁以字幕格為主，頂部「編輯」「工具」「設定」「分享」為按需開啟的入口；「工具」包含劇本解析、參考錄音、即時字幕／演後座談及 JSON 匯入／備份。投影語言、上下排、顏色、音樂效果、字級、寬度與位置放在預覽旁的「投影與顯示設定」。一般演出只顯示簡化字幕格，開啟編輯後才展開復原／重做與選取格的編輯工具；平行檢視、快捷鍵及遮蔽仍可直接使用。這些介面的開關不重建麥克風或辨識連線。

即時字幕是獨立的輸出來源，從「工具 → 即時字幕／演後座談」啟用；可先選座談語言。切換會保存演出場次、CUE、控制方式、演出語言及參考錄音，清除舊辨識文字，讓觀眾與投影同步進入即時字幕；啟動失敗或停止收音時保持即時字幕來源，不會意外顯示上一句劇本。暫停收音保留目前座談文字；「返回劇本字幕」按字幕 ID 恢復位置與原演出設定，原本自動跟戲會重新啟動收音，失敗會明確提示。觀眾網址與 QR、投影頁保持原有連結。只有「設定 → 結束整場活動」會結束活動。

在控制端選好場次，按「自動」並允許麥克風即可。程式直接使用編輯頁已有的字幕清單，不需要另外上傳劇本或提供排練錄音。目前選取的位置是搜尋參考；中途啟動時會核對附近台詞，必要時擴大搜尋。觀眾、提詞與投影端在自動模式都顯示編輯好的劇本字幕，收音只用於定位。若收音已停止，可再次按「自動」重新啟動。手動點選字幕或按上一句／下一句會重新定位並繼續跟戲；需要停止跟戲時請切換「手動」。

自動跟戲由 `server/src/auto-follow.js` 負責：

- 快取字幕的正規化文字、開頭、句尾、下一格位置、完整句重複位置及對齊索引。字幕內容或音樂等標記有變才重建分析；起音時只比對目前與下一格兩筆原始資料，避免套用已編輯的舊準備，不重算整份劇本。
- 以保留字序的連續編輯距離對齊辨識文字與劇本，追蹤格內進度，支援繁簡中文、單字台詞、少量漏字、跨格連續說話，以及一句被拆成多個辨識片段。
- 當完整辨識片段比對偏弱時，額外比對最新 24、16、10、6 字的尾段，讓前段錯字不阻礙後段清楚台詞定位；完整片段已有強證據時優先使用原結果。最近 10 秒內已確認位置、沒有尚待核對的音量預推時，前方 2–4 格的高分且無歧義台詞可直接追上，不必等待辨識定稿。至少需要 6 字的完整台詞或 8 字以上證據；遠距離、往回及位置過期仍保留原有確認流程。重複尾段不盲跳，僅改寫前方雜訊也不算新的遠距離確認證據。
- 格內進度達 70% 且剩餘不超過 3 字時，若比對分數足夠，即提前準備下一格開頭。接近句尾但尚未說完時，仍需起音及有區別的 2–12 字開頭才走格；僅接近句尾不啟用音量預推。
- 恢復受控起音預推：只有位置與目前格句尾已核對完成、下一格緊接在後、兩格皆未標記音樂或舞台指示，且準備未超過 10 秒時，才在至少 120 ms 低音量後、至少 40 ms 持續起音時先走一格。無須等待下一句辨識文字回來；未核對預推位置前，不允許第二次音量預推。
- 穩定跟隨且上一句句尾已確認時，下一格符合的 2 字以上開頭可直接換格或核對預推，不再要求這個開頭在附近所有台詞中都唯一。接近句尾的猜測仍檢查其他台詞的開頭及目前格剩餘內容；起始定位與跳段保留較嚴格門檻。連續說話也可從同一辨識片段新增的開頭文字確認跨格。
- AudioWorklet 每 20 ms 傳送一批音訊；啟動時積存超過 250 ms 的封包仍供辨識使用，但不作為新的起音證據。音量診斷更新有節流，不隨每個音訊封包重繪。
- 順序跟隨與全文校正使用獨立狀態，共用辨識結果，由同一決策流程控制畫面。一次低分或疑似跳詞會取消不可靠的起音準備，但保留最近確認／預推位置最多 10 秒；低分不延長有效期。下一格至少 3 字、且能與目前格內容及附近其他格開頭區分的明確開頭，可直接接手，不必等上一格句尾核對完成。舞台指示與音樂不使用這條快速通道。
- 全文校正即使在順序跟隨可用時也持續核對較長文字；完整搜尋一般每 400 ms 最多一次，final 或待確認候選的文字增長可立即核對。跳段／回跳需要較強證據；暫定結果需隨後續內容再次支持，明確且唯一的 final 可直接校正。全文候選模糊或等待確認不阻止順序跟隨；明確校正才重設跟隨位置。這是判斷狀態獨立，並未另開辨識連線或背景執行緒。
- 以辨識片段 ID、連線 ID 與音訊時間處理過期結果。預推前舊片段的 final 可補入歷史，但不能把畫面拉回或重新啟用預推；新的語音仍可核對跳段或真正的回頭重說。手動定位、切換場次、編輯與重連會清除舊的跟戲依據。
- 辨識服務的 final 只表示該片段定稿，不表示字幕格說完。舞台指示不因 final 自動推進；無聲舞台提示仍需人工 cue 或後續串接獨立舞台訊號。

控制端會顯示比對分數、目前格內進度、準備的下一格開頭、預推待核對狀態、重新定位原因與候選位置。詳細狀態另列順序跟隨保留的位置及全文校正狀態／候選，避免把待校正誤認為順序跟隨已停止。進度是已辨識文字在字幕內的位置估計，不是倒數計時；分數是文字對齊分數，不是正確機率。

「收音診斷」列出最近換格依據、辨識結果抵達時間、辨識落後目前傳送音訊的估計值、文字定位耗時、起音偵測耗時及觀眾／投影／提詞顯示回報往返時間。各顯示角色只接受第一個有效回報，不保存現場音訊。顯示回報在 React 更新後、瀏覽器取得繪製機會時送出，往返值包含伺服器送出至瀏覽器、繪製排程與回傳網路時間，並非精確像素上屏時間或總辨識延遲。沒有開啟或可見的顯示端時會顯示「尚無資料」。

「狀態詳情 → 跟戲歷程與匯出」會保留逐格歷程。開啟自動跟戲或啟動自動收音時自動建立／接續本次紀錄，收合詳情不停止記錄；暫停收音、連線重建、重新整理及手動／自動切換仍接續同次排練。按「結束本次紀錄」後停止累積，按「開始新一次紀錄」或再次啟動自動跟戲會另建紀錄，舊的保留；結束整場活動也會結束紀錄。記錄控制獨立於收音，開始新紀錄不會重啟辨識或改變字幕。只有主動刪除該次紀錄或刪除整個節目才移除資料，沒有自動過期。

- 每次進入字幕格分別保存來源：參考錄音、文字、起音預推、跳詞校正、靜默切換或人工操作；同格的後續錄音／文字確認另外保存，起音預推後得到錄音確認不會改寫原始切格來源。重回同格及人工重新選取目前格會建立新的經過紀錄。起始、版本切換與恢復位置不計為自動觸發。
- 每個場次／劇本／參考錄音版本保留實際台詞與錄音範圍快照。清單可篩選未進入、曾進入但未確認、有人工介入及場次／版本，並展開每次經過；「未進入」僅代表紀錄中沒有經過該格，不等於辨識失敗。人工／自動跨格另有標記；未演到、中途開始、收音中斷及重啟區間需人工核對。已確認表示系統接受配對，並不保證聲學或文字比對正確。
- CSV 為每次經過一列，未進入格也有一列；完整 JSON 另包含依序保存的事件、版本快照、候選與診斷原因、收音串流 ID、現場音訊時間、參考錄音位置及顯示回報。音訊時間在各收音串流內計算，串流重建後歸零，需連同事件序號、伺服器 UTC 時間與串流 ID 比較。同來源同辨識片段保留首次及句尾確認，診斷每通道每五秒最多一筆，不保存逐封包音量或原始現場音訊；比對分數不是正確機率。
- 後端以獨立 SQLite／Postgres `follow_runs`、`follow_events` 表追加事件，通常每 250 ms 小批保存，不重寫整份節目或音檔、不增加 Deepgram／OpenAI 呼叫。寫入錯誤會重試並在狀態列提示；待存事件設有上限，超出時明確記下資料缺口。正常關機會排空待存資料；強制終止或資料庫持續故障可能失去尚未保存事件，重啟後會標記中斷，不能據此判定漏格。沒有持久化磁碟的 SQLite 部署仍受平台磁碟生命週期限制。
- 請一併備份上述兩張歷程表，SQLite → 空白 Postgres 遷移會連同歷程搬移。節目 JSON 備份不包含歷程，需另匯出跟戲 JSON；僅節目擁有者／既有管理權限可讀取或匯出，觀眾與投影端無此權限。新版啟用前未保存的歷程無法補回。

目前沒有加入本機人聲分類或音素辨識模型。符合預推條件時，字幕可早於下一句文字辨識結果切換；若上一句句尾尚未核對、沒有停頓、處於音樂區段或失去位置，仍需等待文字證據。掌聲或音效可能誤觸一次已準備的預推，後續辨識會核對校正；不保證首字零延遲。測試可使用模擬事件，不需要事先有錄音；真實演出延遲、誤跳與跳詞恢復時間仍需現場驗證。

執行離線回歸測試：

```bash
npm test --prefix server
npm run lint --prefix client
npm run build --prefix client
```

測試涵蓋劇本分析快取與編輯失效、辨識延後兩秒仍能依起音預推、不連續盲推、預推後核對與回跳、穩定跟隨與起始定位使用不同門檻，以及顯示回報範圍與去重；保留短開頭、跨格、停頓、跳段、延遲 final、音樂／舞台指示、手動定位、顯示來源及音訊打包測試。包含實際伺服器的收音到換格與跳段校正流程，不會呼叫付費辨識服務。實際聲學準確度與演出延遲需另以現場素材驗收。

收音封包的權限檢查直接讀取已整理的節目資料，避免每秒 50 次收音觸發整份劇本與所有場次重建。跟戲音量與定位診斷使用獨立的 `control:auto-follow` 事件，不附帶整份辨識歷史；只有字幕位置改變才廣播完整畫面狀態。辨識連線的待傳資料設有上限，超過時停止該收音串流並回報錯誤；控制端可再次按「自動」重啟收音。

執行一分鐘本機持續負載測試（需允許監聽本機暫時連接埠）：

```bash
npm run test:audio-load --prefix server
```

此測試以 1,000 格字幕、3 個場次，每秒 50 個 PCM 封包及 10 次模擬辨識事件，經過實際伺服器處理函式，並每秒請求 `/healthz`。輸出健康檢查耗時、事件迴圈延遲、CPU 使用率與字幕重建次數；不讀寫正式資料，不連接雲端辨識服務。另有兩種辨識服務的音訊傳送、權限、重複封包及連線積壓回歸測試。

辨識時間定義參考 [Deepgram 分段與 final 說明](https://developers.deepgram.com/docs/understand-endpointing-interim-results) 與 [OpenAI Realtime 伺服器事件](https://developers.openai.com/api/reference/resources/realtime/server-events)。

## 即時語音辨識（Realtime）接法

目前專案採用「Realtime WebSocket + 輸入音訊轉錄」模式：

1. 後端以 `wss://api.openai.com/v1/realtime?model=gpt-realtime` 建立連線。
2. 連線後送出 `session.update`，`session.type` 使用 `realtime`。
3. 轉錄設定放在 `session.audio.input.transcription`，可使用：
   - `gpt-4o-transcribe`
   - `gpt-4o-transcribe-latest`
   - `gpt-4o-mini-transcribe`
   - `gpt-4o-transcribe-diarize`
   - `whisper-1`
4. 音訊事件使用 `input_audio_buffer.append` 持續送 PCM16(24kHz, mono)。
5. 以前端 `conversation.item.input_audio_transcription.delta/completed` 顯示逐字稿。
6. 後端預設改用 `semantic_vad` 做語意切段，讓 Realtime API 依句意決定何時結束片段；控制端不再提供此選項，預設固定開啟。
7. 語意切段模式下仍保留超時保底 `commit`，若約 2.2 秒都未切出新片段，後端會手動補一次 `commit`，避免長時間完全沒有字幕輸出。
8. 顯示層不再把每個 OpenAI item 硬當成一行；後端會把 completed fragments 重新分組，切段時同時參考 `semantic_vad`、最近靜音長度、標點傾向、最短/最長字數，以及中文不適合切開的位置。
9. 英文與其他拉丁語系片段現在也會額外參考半形字寬、句尾標點與常見英文接續詞，避免句子尚未完成就過早切行。
10. 若偵測到弱邊界（例如 fallback commit 切得太早），後端會把相鄰片段合併後再做一次較高精度的重轉錄/後修正，再回填到同一行。
11. 手動 commit 單一路徑仍可在關閉語意切段時使用（預設約 900ms 一段，且每段至少 400ms 音訊）。
12. 雙通道精修預設固定開啟；快通道完成後，後端會以同段原始音訊做一次 `audio.transcriptions.create` 回填精修。
13. 控制端可額外勾選「辨認講者」；Deepgram 模式會在 Nova-3 串流直接啟用原生 diarization，但字幕文字仍採用完整 final transcript，只以 word 的發音時長投票決定該段主要講者，避免逐字重建及過度切段降低轉錄、精修與翻譯品質。OpenAI 備援模式則會把最近幾行音訊視窗送到 `gpt-4o-transcribe-diarize`。兩種模式都會在檢視端以不同顏色標示不同講者。
14. 控制端可輸入「辨識主題 / 術語提示」；後端會把這份提示同時套用到 Realtime 快通道、雙通道精修與後修正。二次精修與文字後修正會主動運用主題所屬領域的知識判斷同音錯字與專業用語，但只有當音訊或原句及語意都支持時才允許修正，避免為了硬套主題而改變原意。
15. 若「辨識主題 / 術語提示」留白，系統不會送出額外主題 prompt，行為等同目前預設辨識流程。
16. 控制端收音會保留雙聲道輸入並混成 mono，避免 `BlackHole 2ch` 或其他立體聲來源只吃到單邊聲道。
17. 當語言是 `zh`（或 `zh-*`）時，後端會做 OpenCC（簡轉繁，台灣用字）正規化，預設不送額外轉錄提示詞，避免提示詞內容誤出現在字幕。
18. 劇本字幕清單每行可勾選「此處有音樂」；先勾起點再勾終點，控制端會自動把中間整段標成音樂區段，檢視端在該範圍內會固定顯示「此處有音樂」提示。

即時語音預設使用 Deepgram Nova-3 台灣華語模型。請先在後端設定：

- `DEEPGRAM_API_KEY`：Deepgram Project API Key，只可存在伺服器環境變數，不可提交至 Git 或傳到瀏覽器。
- `OPENAI_API_KEY`（選填）：使用 Deepgram 時，可在後端設定此金鑰，將每個 Deepgram final 段落送交 OpenAI 文字精修一次。若控制端已填入 OpenAI API Key，則會優先使用該金鑰；兩者都沒有時保留 Deepgram 原文。

若本機錄音出現「無法取得 Deepgram 短期授權」，先檢查新版本提示中的 HTTP 狀態：401 表示需要檢查後端金鑰是否有效；403 表示 Deepgram 拒絕核發 token，請依[官方說明](https://developers.deepgram.com/guides/fundamentals/token-based-authentication#why-do-i-get-a-forbidden-error)在同一個專案的 API Keys → Create Key → Advanced 建立 Member 或以上權限的金鑰。Member 是 API Key 的權限設定；能做即時辨識的金鑰不一定能核發短期 token。在 Render 的後端服務 Environment 更新 `DEEPGRAM_API_KEY`，儲存並重新部署，完成後在「參考錄音」按「繼續準備／補做辨識」，已保存的片段會重用。429 是授權頻率限制，5xx 或連線逾時則應稍後重試，不應一律更換金鑰。

Deepgram 與 OpenAI Realtime 的 interim 原文會直接顯示，不等待二次精修；若已有觀眾選擇翻譯語言，後端會將最新草稿節流送交 OpenAI 串流翻譯，讓觀眾先看到暫定譯文。暫定譯文採穩定遞增顯示：新結果只會延長相容的既有文字，不會用較短或內容矛盾的串流片段反覆清空、倒退或覆寫畫面。final 原文仍沿用原本的二次精修流程，精修完成後才另外產生正式譯文，並一次取代暫定譯文。草稿翻譯與原文資料完全分開，不會寫回、覆蓋或延遲原文字幕；翻譯超時、失敗或沒有 OpenAI 金鑰時，原文仍照常顯示。「辨識主題 / 術語提示」會同時提供給草稿翻譯及原文精修。

即時語音模式下，檢視端會改用獨立的即時翻譯語言選單（原文、English、日本語、한국어、Español、Français、Deutsch）。後端只會將已有觀眾需求的語言送交 OpenAI 翻譯，且每個 final 段落、每種語言只產生一份共用結果。新加入的觀眾可補齊最近 10 個段落；控制端會顯示各翻譯語言的即時需求人數。選擇翻譯語言後，檢視端只顯示該語言已成功產生的譯文；尚未翻出、處理中或失敗時不顯示原文及狀態文案。只有觀眾明確選擇「原文」才顯示原文。離開即時模式後，檢視端會恢復原本的劇本語言選擇。

控制端可以在「跟戲設定 → 演出語言（現場辨識）」切換繁體中文（台灣）、English、日本語、한국어、Español、Français 或 Deutsch。辨識進行中切換會重建 Deepgram/OpenAI 辨識連線，保留已完成字幕並清除未完成草稿。文字跟戲與錄音切段會依相同語言選擇劇本欄：優先比對語言代碼，再比對中文／English 等語言名稱；「第一語言」等自訂名稱可用「跟戲使用的劇本欄」手動指定，每種演出語言會各自記住設定。舊節目未命名的第一欄維持中文預設；選英文而沒有對應欄位時會提示，不會用中文台詞代替。語言或劇本欄切換會重設定位並排除舊結果，停用不相符的參考錄音。觀眾與投影的顯示語言仍可獨立選擇。檢視端的原文名稱會跟著來源語言變動，並從翻譯目標中排除目前來源語言；當來源不是中文時，觀眾可選擇繁體中文翻譯。

- `LIVE_TRANSLATION_MODEL`：即時字幕翻譯模型（預設 `gpt-4o-mini`）。即時翻譯需要控制端提供 OpenAI API Key，或在後端設定 `OPENAI_API_KEY`。
- `LIVE_DRAFT_TRANSLATION_ENABLED`：是否啟用 interim 草稿的快速串流翻譯（預設 `true`）；設成 `false` 可恢復只翻譯 final 段落。
- `LIVE_DRAFT_TRANSLATION_INTERVAL_MS`：同一語言兩次草稿翻譯請求的最短間隔（預設 `300` 毫秒，最低 `120`）。
- `LIVE_DRAFT_TRANSLATION_MIN_NEW_CHARS`：草稿至少新增幾個字才重新翻譯；遇到標點時不受此限制（預設 `3`）。

控制端仍可切換為 OpenAI 備援；以下環境變數用於微調 OpenAI 即時辨識的即時性與穩定性（後端）：

- `TRANSCRIPTION_SEMANTIC_SEGMENTATION_ENABLED`：控制端未指定時，是否預設開啟語意切段（預設 `true`）。
- `TRANSCRIPTION_SEMANTIC_VAD_EAGERNESS`：語意切段速度，可選 `low` / `medium` / `high` / `auto`（預設 `high`）。
- `TRANSCRIPTION_SEMANTIC_FALLBACK_COMMIT_MS`：語意切段模式下，最長等待多久仍沒切段就強制補一次 `commit`（預設 `2200`）。
- `TRANSCRIPTION_SILENCE_LEVEL_THRESHOLD`：判定最近輸入是否接近靜音的音量門檻（預設 `0.012`）。
- `TRANSCRIPTION_BOUNDARY_MIN_CHARS`：偏短片段不容易直接斷行（預設 `10`）。
- `TRANSCRIPTION_BOUNDARY_SOFT_MAX_CHARS`：到達這個長度後更傾向斷行（預設 `26`）。
- `TRANSCRIPTION_BOUNDARY_HARD_MAX_CHARS`：超過這個長度時強制開始新行（預設 `38`）。
- `TRANSCRIPTION_BOUNDARY_WEAK_PAUSE_MS`：短停頓加分門檻（預設 `120`）。
- `TRANSCRIPTION_BOUNDARY_STRONG_PAUSE_MS`：強停頓加分門檻（預設 `320`）。
- `TRANSCRIPTION_FORCE_COMMIT_INTERVAL_MS`：commit 週期（預設 `900`）。
- `TRANSCRIPTION_MIN_COMMIT_AUDIO_MS`：最小音訊長度才 commit（預設 `400`）。
- `TRANSCRIPTION_COMMIT_COOLDOWN_MS`：兩次 commit 的最小間隔（預設 `500`）。
- `TRANSCRIPTION_DUAL_CHANNEL_ENABLED`：控制端未指定時的雙通道精修預設值（預設 `true`）。
- `TRANSCRIPTION_SPEAKER_RECOGNITION_ENABLED`：控制端未指定時，是否預設開啟講者辨認（預設 `false`）。
- `TRANSCRIPTION_SPEAKER_WINDOW_MAX_LINES`：每次講者辨認時最多合併幾行近期字幕（預設 `4`）。
- `TRANSCRIPTION_SPEAKER_WINDOW_MAX_MS`：每次講者辨認視窗的最大音訊長度（預設 `16000`）。
- `TRANSCRIPTION_ACCURATE_MODEL`：二次音訊精修模型（預設 `gpt-4o-transcribe-latest`）。
- `TRANSCRIPTION_ACCURATE_PROMPT`：二次音訊精修用提示詞（選填）。
- `TRANSCRIPTION_ACCURATE_MIN_SEGMENT_MS`：二次精修最短片段長度（預設 `400`）。
- `TRANSCRIPTION_ACCURATE_MAX_SEGMENT_MS`：二次精修最長片段長度（預設 `8000`）。
- `TRANSCRIPTION_ACCURATE_MAX_PENDING_SEGMENTS`：等待對齊的音訊片段上限（預設 `40`）。
- `TRANSCRIPTION_TRADITIONAL_OUTPUT_ENABLED`：是否啟用繁體輸出保證（預設 `true`）。
- `TRANSCRIPTION_TRADITIONAL_OUTPUT_PROMPT`：自訂轉錄提示詞（選填，預設空值；若設定可能增加提示詞洩漏到字幕的風險）。

### 常見錯誤對照

- `Missing required parameter: 'session.type'.`
  - `session.update` 缺少 `session.type`。
- `Invalid value ... Supported values are ...`
  - 事件名稱或 payload 結構仍是舊版（例如舊的欄位位置）。
- `Passing a transcription session update event to a realtime session is not allowed.`
  - 連線是 realtime session，卻送了 transcription session 形狀。
- `Model "gpt-4o-mini-transcribe" is not supported in Realtime API`
  - 通常是把轉錄模型誤當成 WebSocket 連線模型（query `model=`）送出。

## 其他注意事項

- 後端目前採用雙儲存策略：
  - 若有設定 `DATABASE_URL`，優先使用 PostgreSQL
  - 若未設定 `DATABASE_URL`，才 fallback 到本機 SQLite
- 首頁目前採用封閉式帳號登入；公開註冊預設關閉，新帳號需由管理員後台建立。第一次部署請設定 `ADMIN_BOOTSTRAP_USERNAME` 與 `ADMIN_BOOTSTRAP_PASSWORD` 來建立初始管理員。
- 登入後會先進入節目列表；不同節目各自保存場次、字幕、語言、角色、投影設定、viewer/projector 連結。管理員可看到所有節目，操作員只看到自己建立的節目。
- 共用控制密碼仍保留為臨時入口；若未設定環境變數，預設密碼為 `20141017`。可用 `SUBTITLE_MACHINE_ACCESS_PASSWORD` 覆寫。
- 匯入節目備份會建立一份新的節目副本，不會覆蓋既有節目。
- Render 部署建議直接綁定 Render Postgres，平台會自動提供 `DATABASE_URL`，此時帳號、登入 session 與字幕節目資料都會寫進 Postgres，不會因 redeploy 消失。
- 若你使用 Render 免費 Web Service，又不打算加購 Persistent Disk / Postgres，請把「節目備份 JSON 匯出 / 匯入」當成正式備份流程；免費環境的本機檔案系統不適合長期保存字幕資料。
- SQLite fallback 模式的預設資料庫位置不在 repo 內，而是在系統使用者資料夾：
  - macOS：`~/Library/Application Support/subtitle-machine/app-store.sqlite`
  - Linux：`~/.local/share/subtitle-machine/app-store.sqlite`
  - Windows：`%APPDATA%/subtitle-machine/app-store.sqlite`
- SQLite fallback 依賴 `node:sqlite`；若你不使用 `DATABASE_URL`，請確認 Node.js runtime 支援該模組。
- 若未使用 `DATABASE_URL`，可用 `SUBTITLE_MACHINE_DATA_DIR` 指定自訂 SQLite 資料夾；伺服器啟動時若偵測到舊的 `server/data/app-store.json`，會自動搬遷到新的儲存層。若已切到 Postgres，系統也會嘗試把既有本機 SQLite / 舊 JSON 內容匯入 Postgres。
- 控制端的 QR code 現在改為本地產生，不會再把 viewer 亂碼網址送到第三方 QR 服務。
- 忘記密碼流程已改成「送出申請，請管理員於後台協助重設」，前台不再直接取得重設碼。
- 若要部署到正式環境，至少應設定：
  - `ALLOWED_ORIGINS=https://你的網域`
  - `ADMIN_BOOTSTRAP_USERNAME=你的管理員帳號`
  - `ADMIN_BOOTSTRAP_PASSWORD=你的管理員密碼`
  - `COOKIE_SECURE=true`
  - `COOKIE_SAME_SITE=lax`（若前後端真的跨站，才考慮 `none`，且必須同時開 `COOKIE_SECURE=true`）
  - `TRUST_PROXY=1`（若前面有 Nginx / reverse proxy / platform proxy）
- 若部署在 Render，建議 Web Service 直接綁定 Render Postgres，並至少設定：
  - `DATABASE_URL`：Render 會自動注入
  - `POSTGRES_SSL=true`：若連的是需要 SSL 的 Postgres 連線
  - `ALLOWED_ORIGINS=https://你的正式網域`
  - `ADMIN_BOOTSTRAP_USERNAME=你的管理員帳號`
  - `ADMIN_BOOTSTRAP_PASSWORD=你的管理員密碼`
  - `COOKIE_SECURE=true`
  - `TRUST_PROXY=1`
  - 使用 Postgres 時不需要再掛 Persistent Disk 來保存帳號或場次資料
- 為避免洩漏，控制端不會在伺服器保存 OpenAI Key；需於控制端畫面手動輸入。
- 若需要部署到雲端，請確保 3000 連接埠（或自訂）對控制端與檢視端裝置開放，並可依需求設定 HTTPS。

### 彩排錄音與音訊跟戲

控制端「工具 → 參考錄音」以本機檔案準備參考錄音。支援超過三小時的錄音，單份最長 12 小時，每個節目最多 5 份；新錄音不受舊版 128 MB 原檔上傳上限限制。請使用新版桌面 Chrome 或 Edge，支援的格式依瀏覽器解碼能力而定，常用 WAV、MP3、M4A 已驗證。原音檔以 BlobSource 按需讀取，背景 Worker 每次只解碼五分鐘與邊界的兩秒重疊，不把整份錄音載入 PCM 記憶體。

1. 選擇「連結本機錄音並自動切段」。原檔及 PCM 不傳送到 Render；瀏覽器以短期 token 把每段 16 kHz 單聲道 WAV 直接送 Deepgram，後端只保存 RFA1 聲音特徵、100 ms 波形、辨識文字與整份錄音的時間戳。`DEEPGRAM_API_KEY` 保留在後端，需有核發 token 的 Member 權限；沒有金鑰時仍能準備聲音特徵及手動標記。辨識請求帶 `mip_opt_out=true`，不參與 Deepgram 模型改善；供應商處理與用量紀錄依其政策。
   每段完成後保存進度，可停止後按「繼續準備／補做辨識」。已保存的辨識結果會重用；辨識成功但分析資料上傳失敗時，也會先保留本機 checkpoint，避免正常續傳時重複辨識。若關閉分頁時供應商已處理但回應未收到，仍可能需要重試該段；這不是保證只計費一次的交易。
   桌面 Chrome／Edge 優先保存本機唯讀檔案控制代碼；若無此 API，會嘗試把 File 副本保存在這台電腦的 IndexedDB。瀏覽器可能再次要求權限，清除網站資料、改網址、換瀏覽器／電腦或原檔被修改時需重新連結；連結時以分塊 SHA-256 雜湊鏈核對內容。已完成的伺服器跟戲不依賴本機原檔是否已連結，只有試聽及重新辨識需要原檔。檔案連結／副本是這台瀏覽器的資料，不會經節目同步傳給其他裝置。
   錄音語言預設跟隨演出語言，也可單獨指定。修改語言後舊辨識進度失效，請連結原檔並繼續準備；只改劇本文字或劇本欄時，可用既有辨識結果重新切段，不必重送音檔。現有雲端錄音仍可播放、辨識與跟戲。
   「匯出分析備份」下載 `.subtitle-audio`，包含聲音特徵、波形、辨識結果與片段校正，**不含音檔**。換電腦或還原節目時，先還原節目 JSON，再匯入各份錄音分析備份，可恢復對應標記；若劇本識別碼已改變，請重新自動切段。音檔請自行備份，試聽時再連結。節目 JSON 本身不包含聲音特徵。

2. 系統依現有字幕格與劇本順序建立片段。同時搜尋完整相同與有漏字／加字／錯字的候選，用前後清楚台詞與人工定位點限制搜尋範圍；短台詞也會嘗試近似配對。重複台詞、詞內估計切點、長停頓與文字不一致會標成待確認，不能只靠高辨識信心自動啟用。舞台指示不當成台詞音訊。
3. 選字幕格會同步定位到起點，按「試聽片段」播放該格範圍；播放中切換上一格／下一格會停止舊片段並試聽新格，暫停中換格保持暫停。可拖曳波形上的起點／終點、放大片段、輸入秒數或採用目前播放位置。按「確認並保存範圍」後鎖定該格，重新自動切段、時間校正與 AI 補對齊都保留有效的人工校正。可「重算這格附近」（前後各五格），其餘字幕保持原範圍；需要修改鎖定格時可直接再保存，或先「解除校正鎖定」。
4. 核對片段後按「使用此錄音跟戲」。正式收音仍持續進行文字辨識；可靠音訊可先換格，文字先確認也會立即換格。兩者共用目前 CUE，不會因另一個結果晚到而重複前進或倒退。場次不符、片段未對齊／已失效或音訊比對不可靠時，沿用文字跟戲。
5. 字幕文字、類型或識別碼改變後，對應片段會標成失效，需重新切段或校正。手動定位、停止收音、停用錄音和場次切換會重設音訊追蹤；音訊確認句尾也能使用既有的「靜默 3 秒進入舞台指示」清屏規則。

試聽與分析共用解碼器及整數樣本時間軸，由背景 Worker 按需解碼 20 秒區塊，再以 Web Audio 播放精確範圍，避免長 MP3 的快速跳秒索引把聲音定位到較早內容。保留一般單／雙聲道音質（最高 48 kHz），只快取少量附近區塊，不載入整份長錄音的 PCM。片段停止、連續播放、進度條、辨識詞定位及手動校正共用原音秒數；準備下一段時若解碼較慢，暫停時間軸等待，不略過聲音。修正播放不需重新辨識，也不改動既有對齊資料。前端播放回歸測試可在 `client` 執行 `npm test`。

「辨識原文與時間核對」分頁顯示每個詞的原始辨識時間、校正後播放時間與對應字幕格，可查看目前字幕／播放位置附近或翻頁，每次只載入 120 個詞。新錄音以整數樣本位置核對每批的實際長度、16 kHz WAV 時鐘與供應商回報長度；解碼總長或音軌起點不同時會提示。舊分析仍可直接重新切段，不必重送 Deepgram。

辨識詞若只有同一個起終時間，保留文字與該時間點，相關字幕標為待確認，不臆測時長或移動後續詞。尾端原有的 0.1 秒容差若裁回片段邊界，也標記時間待確認。單個詞超界、缺少時間或終點早於起點時，保留該詞的原回傳時間、批次、詞編號、異常原因與有效的 Deepgram 查詢編號，隔離其時間，不中止其他詞與後續批次。供應商回報的整批音訊長度與實際送出的樣本時鐘不符時仍停止，避免把錯誤時間基準套用到整批台詞。

新批次保存完整的有效重疊區辨識結果，待相鄰批次都完成後，以文字、時間及順序比對交界，優先採用所屬批次的完整詞，避免兩邊各自依時間中點篩選造成漏詞。相同詞只在相鄰批次的共用區間作一對一合併，不合併同一批內真正重複說出的詞。只能採用另一批的參考詞、兩批結果互相衝突或詞時間不完整時，相關字幕保留待確認狀態。全程使用原音的絕對秒數，不累加裁切後長度。

例如第二批送出原音 298～602 秒，回傳的詞在該批 303.705～305.145 秒（原音 601.705～603.145 秒），會保留異常紀錄並繼續第三批；第三批若取得同位置的完整詞，就以第三批結果補回。補不回來時只標記附近字幕待確認，其餘批次仍可完成。面板顯示補回／待確認數量，「辨識原文與時間核對 → 分批交界與異常詞紀錄」可查看原始時間與來源批次；紀錄也包含在分析備份中。舊版已保存的批次可繼續重用。此流程不會自動追加付費辨識；尚未補回的範圍可試聽並人工校正。

固定偏移時，選一個詞，將原檔停在該詞實際起音處，按「以目前播放位置校正選定詞」，再套用時間校正。若誤差隨時間增加，加入相隔較遠的第二個定位點校正比例，建議加第三個點驗證。定位點不符合共同的比例與偏移時拒絕整體校正，應核對切段交界；不會自動把不連續錯誤拉伸成同一時間軸。原始 ASR 時間保持不變，校正僅保存轉換參數；字幕片段採校正後時間，波形與聲音比對預設保留原分析時鐘；若核對後確認波形本身也與原檔偏移，才勾選「波形也與播放位置偏移，一併校正波形與聲音比對」。兩個時鐘分開保存，避免修正 ASR 偏差時移走原本正確的波形。人工範圍不移動。可隨時恢復原辨識時間；校正參數與定位點也包含在分析備份中。

可按「AI 補對齊待確認片段」或「AI 核對這格附近」。使用控制頁設定的 OpenAI 金鑰（只在該次請求使用、不寫入伺服器資料）或後端 `OPENAI_API_KEY`，預設模型 `gpt-4o-mini`，可透過 `RECORDING_ALIGNMENT_MODEL` 覆寫。僅將有限範圍的辨識文字、固定詞編號、附近劇本和定位點送到 Responses API（`store:false`），不送音訊；模型回字幕 ID 與起終詞編號，允許不確定，禁止自行給秒數。程式另外驗證詞編號、文字證據、定位點、範圍與順序；有字詞差異或邊界疑慮仍需試聽。有效回應會快取，正常續作不重複要求同一批；每次最多 12 批，可用 `RECORDING_ALIGNMENT_MAX_BATCHES` 設定 1～20 批。失敗保留原結果，可停止後重試。AI 文字請求另計 OpenAI 用量，不會為了補配對重新辨識音檔。

聲音比對使用正規化頻譜特徵與有界的即時 subsequence DTW，在獨立 worker thread 中執行，不等待語音轉文字結果，也不按彩排的固定秒數播放。這是參考錄音的聲學比對，尚未用真實彩排驗證；演員聲音、環境、語速和即興內容的差異可能使音訊無法可靠定位，文字通道仍持續校正。狀態詳情會標示實際換格依據，錄音面板會顯示聲音相似度（不是經校準的辨識正確機率）。

原始錄音、特徵和辨識時間戳分開存入目前使用的 SQLite／Postgres `recording_assets` 表；CUE 更新只保存小型節目資料，不重寫音檔。既有的 SQLite → 空白 Postgres 自動遷移會一起搬移錄音資產。請將該表一起納入資料庫備份。字幕 JSON 備份包含對齊標記，**不包含音檔**；跨環境匯入 JSON 後需重新匯入參考錄音。移除錄音或刪除節目會清除相關音訊資產。處理途中重啟會標示「處理中斷」，可重新切段接續；錄音分析與即時跟戲失敗不會停止文字辨識。

## Node.js 安全更新與 Render 部署

- 專案使用 Node.js `22.23.4`，根目錄及 `server/`、`client/` 的 `.node-version` 均指定相同版本，支援分別設定 Render Root Directory。前後端 `package.json` 的 `engines.node` 限制為 `>=22.23.4 <23`。
- 本機開發、測試及負載測試也請使用此修補版；未來升級 22.x 修補版時，請同步更新三份 `.node-version`。
- Render 的 `NODE_VERSION` 環境變數優先於專案設定。若後台已有此變數，請更新為 `22.23.4` 或移除以採用專案設定。
- 這次更新對應 [Render eMudhra 公告](https://render.com/docs/advisory-emudhra) 與 [Node.js 2026-10-21 安全更新](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)。只更新 npm 套件不能取代 Node.js runtime 更新。
- 所有相關 Render 原生服務（包括前端建置）都需重新建置及部署，才會更新 runtime 與系統憑證庫。若未啟用自動部署，請執行 Manual Deploy → Deploy latest commit。
- 部署前確認資料使用 Postgres 或持久磁碟，並備份節目；避開演出時段。部署後從建置紀錄及服務 Shell 的 `node --version` 確認為 `v22.23.4`，再驗證登入、字幕同步及 OpenAI／Deepgram 功能。
